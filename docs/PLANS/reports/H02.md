## Deviations from the plan

1. **`ResearchInventory.played_items`.** The plan's field list has only `pool`,
   `sectors`, `played`; `plan_research_removal` cannot compute the played-core
   removal from those (the facade reads the played sector's live core rows).
   Added `pub played_items: Vec<(String, i32)>` (additive field; documented).
2. **`&mut SettingsStore` instead of `&mut dyn SettingsStore`/`&mut dyn UnlockStore`.**
   `SettingsStore` is a concrete struct in this crate (not a trait), and
   `Campaign::run_turn`/`Sector::save_info`/`Planet::set_last_sector` take it.
   `begin_sector_launch` therefore takes the store and wraps it in
   `tech_tree::SettingsUnlockStore` internally; `run_due_turn`,
   `run_turn_now` and `apply_resume_record` take `&mut SettingsStore`.
3. **Two launch fns were chosen** (`begin_sector_launch` +
   `clear_being_played_for_launch`), as the two blocks are separated by the host
   side effects (corrupt-save handling, lost replay, loadout parse) in the
   facade. `clear_being_played_for_launch` duplicates H01's
   `Campaign::clear_being_played`; X01 must use H01's and C01 removes ours.
4. **`capture_played_sector` is the forced-capture wrapper, not a system call.**
   At the branch base the `game_state_tick_system` capture arm is already
   extracted into `on_captured_sector` (the 02-FINDINGS #2 resolution), and the
   system calls it. So the system needed no change (making it call a forced
   `sector_capture` would double-capture). The new fn snapshots the listener
   inputs, runs `sector_capture`, applies `on_captured_sector` and queues the
   events — i.e. today's facade body, including `service.on_sector_capture`
   (the package's "do not add it" note predates the findings resolution). X01
   keeps its own body per its own package, so the fn stays uncalled for now.
5. **`LaunchReject` has two variants.** The third early return (unknown planet)
   cannot occur because the signature takes `PlanetId`; the facade resolves the
   name first. The facade has no toast on these paths (only `log::warn!`), so
   the variants carry no toast key.
6. **`live_sector_record` takes the campaign to read from.** The facade read the
   record from the taken runtime when installed (`runtime_or_facade_record`);
   X01 must pass the runtime's campaign in that path. The planet-name/settings
   early exit stays in the facade.
7. **`apply_resume_record` resolves the planet name through the registry** (the
   signature has no planet-name parameter). It also keeps the facade's order:
   record write -> `has_core` -> `save_info` -> inventory refill ->
   `planet.apply_rules`.
8. **Not run:** `run --cargo-test -p mind-headless` (the package's verification
   lists it, the parent's required-check list does not; S02 recorded it red at
   the base on the stale `render_layers_full` golden). Determinism exercises the
   headless binary. `run-all --tier T0` does not cover the campaign scenarios;
   see Verification.

  `tech_tree.rs` rows with the campaign API surface.
- **Behaviour bugs noticed (NOT fixed):**
  - `game/launch.rs` `item_on_planet` (copied verbatim from
    `campaign/launch.rs:510-514`) diverges from Java
    `UnlockableContent.isOnPlanet` (`Mindustry/.../UnlockableContent.java:132-134`):
    Java also returns true for `planet == sun`, `planet == null` and an **empty**
    `shownPlanets`, while the port checks `contains` only. Vanilla items carry no
    `shownPlanets` (only tech-node contents get them), so the launch dialog's
    `resources` filter drops every item on a planet that allows launch loadouts.
    Needs its own parity fix + test; the copied helper must keep today's
    behaviour until then.
  - `game/runtime/game_state.rs` `game_state_tick_system` snapshots
    `was_attack_mode`/`buildings_destroyed` before `check_game_state`, which is
    correct for the capture listener, but `check_game_state_campaign` can return
    `SetRules` before a later capture in the same call; no capture can follow a
    `SetRules` in one call (`attack_after_waves` only converts waves->attack),
    so this is observational only.
