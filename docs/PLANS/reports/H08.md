### Helper bodies (byte-equivalence notes)

- `sorted_by_seq(it)` collects `(seq, entity)`, `sort_by_key(|(seq, e)| (*seq, e.index()))`
  and returns the entities. It is the exact key and sort function; the two checksum
  sites fold the seq, so they re-read `EntitySeq` from the same live entity in the loop
  (identical value — a checksum never mutates the world, and the golden/determinism
  gates confirm the byte stream).
- `team_of(world, e)` = `world.get::<TeamComp>(e).map(|t| t.team)`.
- `unit_def(world, content, e)` = `world.get::<UnitTypeComp>(e)` then `content.unit(id)`.
  Every adopted site did nothing between the two lookups (verified site by site).
- `tile_world(tile)` keeps the `unit_runtime` expression (`tile.x() as f32 * TILE_SIZE`,
  `TILE_SIZE = crate::config::TILESIZE as f32`), numerically identical to the deleted
  `builder` copy's `f32::from(x) * unit`.
- `with_unit_runtime_removed(world, f)` removes the runtime, runs `f(world, &mut runtime)`,
  re-inserts it and returns `Some(result)`; `None` when the resource is missing. While
  removed, nested code still sees no runtime, exactly like every converted pair. No
  `get_non_send(_mut)` site was converted.
- `dist2(dx, dy)` = `dx * dx + dy * dy`, verbatim: no `mul_add`, `hypot`, `f64`, FMA
  contraction or reassociation.

## Deviations from the plan

1. **`sorted_by_seq` is `-> Vec<Entity>` as specified, at the cost of one seq re-read at
   the checksum sites.** The plan lists `ur:586`/`ur:619` (the `UnitRuntime::checksum`
   units and bullets) and `runtime:1202` (the `SimRuntime::checksum`) as replaceable, but
   those loops fold the seq they sorted by. The helper keeps the specified `Vec<Entity>`
   return and each checksum loop re-reads `EntitySeq` from the same entity; the value is
   identical (both are `map(|s| s.0).unwrap_or(u64::MAX)` on an untouched world), and the
   checksum gates pass. The alternative (returning `Vec<(u64, Entity)>`) deviates from the
   package signature, so it was not taken.
2. **`ur:1003` (`dead.sort_unstable_by_key` in `resolve_deaths`) is not adopted.** The
   helper table lists it, but the Explicitly-forbidden section says "do not touch
   `resolve_deaths`". The prohibition wins; `resolve_deaths` is untouched (its two
   `remove_non_send` pairs and its four `team_of`/four `unit_def` sites are also left in
   place). Follow-up for the `resolve_deaths` owner (X02/C01) to adopt them.
3. **`unit_update_system` sites left in place** (forbidden: X02 owns the body). That
   excludes one `TeamComp` read, seven `content.unit` lookups and one remove/insert pair.
4. **Sites that only read `UnitTypeComp::type_id`** (for a different content lookup, or to
   compare ids) are not `unit_def` sites and were left alone: `player.rs` docked-type
   reads (x3), `builder/update.rs:91`, `builder/checks.rs:194`, `runtime/teams.rs:114`,
   `debug.rs` 4-tuple destructure. `unit_def` replaces only the adjacent
   `get::<UnitTypeComp>` → `content.unit(id)` pair, as specified. This is why the helper
   table's "about 45 sites" became 25 adoptions.
5. **`tile_world`: one implementation in `query.rs`, not the `unit_runtime` copy left in
   place.** `unit_runtime::targeting` is a private module, so `builder::checks` cannot name
   it; a `pub(crate)` query item plus `pub(super) use` re-exports in both files keeps both
   old paths (`unit_runtime::targeting::tile_world`, `builder::checks::tile_world`)
   resolving and leaves exactly one body.
6. **`UnitDef` in the plan is `UnitTypeDef`** (`crate::content::registries::units::UnitTypeDef`).
   There is no `UnitDef` type in the registry.
7. **The 19th remove/insert site is a test fixture** (`unit_runtime/tests.rs:1007`); H07
   owns test files, so only the 15 eligible non-test pairs were converted.
