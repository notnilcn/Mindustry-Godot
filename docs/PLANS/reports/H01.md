## Deviations from the plan

1. **`Sector::display_name` already exists** at the branch point: `a99b5c67` ("consolidate sector
   display names", findings #3/#4) added it to `sector.rs` and deleted the private
   `ui/campaign.rs` `sector_display_name` the package points at. No code was added; the existing
   `display_name_matches_java_precedence` test covers the Java precedence.
2. **`SettingsStore` is a concrete struct, not a trait.** The package signatures spell
   `&mut dyn SettingsStore` / `&dyn SettingsStore`; the functions use `&mut SettingsStore` /
   `&SettingsStore` (no `dyn` trait exists to name). Behaviour is unchanged.
3. **`save_sector_info` returns `Result<bool, IoError>`** (the table's type; `bool` = the
   planet and sector resolved and the record was written) even though the prose says "the exact
   return type of `Sector::save_info`" (`Result<(), IoError>`). The `bool` is what expresses the
   facade flush's "sector present" check, and every facade call site ignores the error.
4. **`launch_resource_stacks` has two facade copies, not three.** The package cites 6170-6177,
   6389-6401 and 6431-6438; 6431-6438 is `dense_from_names`, not this conversion. The two real
   copies differ (`> 0` + break vs `!= 0` + `unwrap_or(0)`); per RULES §4 the helper implements
   the `get_launch_resource_stacks` form (6170-6177) and its doc says the launch dialog site
   (6389-6401) must keep its local copy.
5. **`dense_from_names`**: the 5405-5416 copy adds (`+=`), the 6431-6438 copy assigns; the
   helper is additive. The second site's pairs come from an `IndexMap`, so its names are unique
   and both forms agree there; the first can receive repeated stacks, where additive is the
   behaviour. No clamping exists in either copy.
6. **`fill_module`** copies disagree superficially (`play.rs` no explicit clamp with an
   `i32::MAX` add cap; `runtime/session.rs` `max(0)` with the core capacity; facade
   `clamp(0, capacity)` with an `i32::MAX` add cap). `ItemModule::add` already clamps
   `(stored + amount).clamp(0, capacity)`, so `clamp(0, cap)` + `add(..., cap)` is equivalent to
   all three; the test pins clear/clamp/unknown-name behaviour.
7. **`own_sector` was not added.** F3 found no canonical body (save-name construction, capacity
   and extra fields differ across 17 sites); adding one variant would be a behaviour change for
   the others (RULES §4). `test_support.rs` documents the omission and the F3 report lists the
   variants.
8. **`set_campaign_rules` is `() -> ()` per the table** (no `SettingsStore` parameter): it only
   writes `planet.campaign_rules`. Persistence stays with the caller's `save_all`; re-applying
   to the played session is H02's `play::reapply_planet_rules`.
9. **`edit_sector` ignores `save_info`'s error**, exactly like all nine facade sites (`let _ =`);
   an unknown planet/sector returns `None` and writes nothing.
10. **Line-number citations are the package's 291e30a8 facade numbers**, as the package asks;
    the code was located by function name in the S01 split (`campaign/{sectors,lifecycle,rules,
    sector_launch,launch}.rs`), where module paths differ but bodies are unchanged (S01 verified
    verbatim).
11. **Test-helper adoption scope**: `saves.rs:700` and `planet.rs:648` were the two named local
    copies; `sector.rs`'s two inline boots and `universe.rs`'s `make_campaign` were adopted too.
    `campaign_rules.rs` has no `create_base_content` copy.
