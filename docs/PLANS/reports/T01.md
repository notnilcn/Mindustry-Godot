## Deviations from the plan

1. **Snapshot capture order / method.** The package says to call the *current*
   pure JSON pieces first; they were `&self` methods of the Godot class and
   therefore not callable from a headless unit test. Instead the same expected
   bytes were generated from the verbatim pre-T01 `json!` layout (rebuilt from
   the fixture inputs in a temporary `#[ignore]` test) and are now checked in;
   the committed test only compares `serde_json::to_string(&typed)` against
   them. The moved statements were diffed against the removed facade bodies;
   their values are additionally covered by the 8 core model tests and the
   seeded-fixture assertions.
2. **`ResearchReqRow.have`/`need` are `String`**, not `i32` as the plan sketch
   suggested (the current JSON carries `format_amount_default` text, e.g.
   `"42[gray]k[]"`), and **`ResearchNodeRow.progress` is `i32`** (`-1` = no
   bar), not `f32`. The plan said to read the `json!` calls and match them, so
   the structs match the real payload.
3. **`get_launch_resource_stacks`** keeps the object shape by collecting the
   typed `Vec<(String, i32)>` into an `IndexMap` before `to_gstring` (a bare
   `Vec<(String, i32)>` would serialize as pair arrays). Only nonzero entries
   are emitted, as before.
4. **`SectorStateView.sector` is `i64` with `-1` as the no-sector sentinel**;
   `sector_state_dict` gates the record-row group on `sector >= 0`, which is
   exactly the old `session.sector.is_some()` gate (`sector_state_rows`
   returned an empty `Vec`). All other view fields mirror the old dict values.
5. **`get_sector_state` has no JSON form**, so its equivalence proof is the
   engine-gated key/type test (PAR-0586) rather than a golden; the mapping in
   `sector_state_dict` is a one-to-one field projection.
6. **`CampaignText::content_emoji` is a required method**, not defaulted: the
   facade reads `MindAssets.unicode_str`; the defaults for the derived text
   helpers are provided on the trait. `content_icon_name` moved to core and the
   facade helper (still used by `campaign/database.rs`) now delegates to it, so
   there is one implementation.
7. **Persistence ordering in `launch_plan`:** the recomputed launch sequence is
   persisted after the view is built instead of before the JSON assembly, since
   the view is what carries `resources` now. `persist_planned_resources` runs
   under the same `destination_allow && max` gate and writes the same dense
   sequence (`view.resources` is the zero-filtered `plan.resources`; dropping
   zero rows from `dense_from_names` is a no-op). No read depends on the order.
8. **`campaign/views_snapshot_tests.rs` lives next to `views.rs`** (compiled as
   a `#[cfg(test)] mod` of `campaign.rs`) rather than under `campaign/testdata/`;
   the snapshots themselves are `campaign/testdata/*.json` as the package
   specifies.
