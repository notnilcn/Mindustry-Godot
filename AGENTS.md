# AGENTS.md — Mindustry-Godot (repo root)

Mindustry-Godot is a 1:1 parity port of [Mindustry](https://github.com/Anuken/Mindustry)
(Java + Arc, GPL-3.0) to a **pure-Rust Godot 4.7 client** (`godot-rust` GDExtension with
`bevy_ecs` used as a library) backed by **SpacetimeDB**. There is no C# anywhere.

The whole game — deterministic fixed 60 Hz simulation, content, world, IO, campaign,
units/combat/AI, logic (mlog), render data, UI/input models — lives in Rust under
`client/rust/`. The Godot tree under `client/` owns scenes and GDScript UI and holds no
game rules. `mind-core` is Godot-free and tokio-free and runs under a bare
`cargo test -p mind-core`; the headless oracle (`mind-headless`) drives the same core
without a window, and the SpacetimeDB server relays commands and keeps persistent state.

This root file is a **pointer and workflow contract**. Read the `AGENTS.md` nearest the code
you are about to touch.

## Build, run, verify

Run from the repo root. The `.sh` scripts are canonical on the Linux dev host and run the
relative `cargo` commands below.

## Parity feedback loop

Player-visible parity is verified in-engine, not asserted from docs. The loop:

1. The `gap-identifier` subagent (`.opencode/agent/gap-identifier.md`) compares
   the port under `client/` against `../Mindustry` and records code-sourced
   candidates in `.opencode/evals/findings.json` (`add --source code`) with
   file:line evidence on both sides and a repro sketch. This stage is cheap and
   runs in parallel across areas.
2. Implementers read the ledger, fix one `EV-####` at a time in game code, and
   claim it in the commit message (`Fixes EV-0001`). The gap identifier then
   re-reads the diff and marks it `code-verified`.
3. The `evaluator` subagent (`.opencode/agent/evaluator.md`) is the final gate:
   it drives the Java reference with computer-mcp and the Godot client with
   open-godot-mcp, re-runs the finding's exact repro, and is the only judge of
   `verified-fixed`. Run reports live under `.opencode/evals/runs/` (local
   evidence, not committed).
4. `/parity-gap` runs a code-scan wave; `/parity-loop` drives one
   identify → fix → code-verify → final-verify iteration; `/parity-eval` runs
   the in-engine half alone. MCP use is slot-gated
   (`.opencode/skills/parity-eval/scripts/mcp_slot.py`, `MCP_SLOT_LIMIT`
   default 2), and computer-mcp needs `DISPLAY` at opencode process start.
   Working MCP sequences live in `.opencode/chains/`.

Docs, plans and gate reports are claims until a running client reproduces them;
a code-sourced candidate is a falsifiable claim until the evaluator runs its
repro in-engine.

## Workflow rules

- **Document current state only.** `AGENTS.md` files, code comments and docs describe how the
  code works **now**, in the present tense. Never add history or changelog narration — no
  "previously", "used to", "was replaced", "now migrated", "legacy", or phase/milestone
  framing. If a change alters structure, responsibilities or invariants, update the relevant
  `AGENTS.md` rather than leaving a note about the change.
- **Stale root artifacts are not sources of truth.** The `*_PLAN.md` files and `old_AGENTS.md`
  in the repo root are old planning/scratch material. Do not read them for context and do not
  propagate their roadmap or plan-number language into code, comments or docs.
- **Respect the crate boundary.** `mind-core` stays Godot-free and tokio-free; `mind-gdext`
  holds no game rules and only bridges Godot to `mind-core`; GDScript is UI-only and never
  mutates simulation state. Hosts call into `mind-core`, never the reverse.
- **Never hand-edit generated files.** SpacetimeDB bindings
  (`client/rust/mind-stdb/src/module_bindings/`), packed assets under `assets/`, the
  `client/scenarios/` mirror and generated manifests are produced by tooling and overwritten.
  Regenerate with the owning script (`server/build.sh`, `tools/pack.sh`, `tools/sync_scenarios.sh`).
- **Keep paths relative and host-neutral.** Scripts, docs and commands reference files
  relative to the repo root or to the file that owns them — never an absolute machine
  path. Host installs are resolved through environment overrides (`GODOT_BIN`, `MINDY_SRC`,
  `OPEN_GODOT_MCP_BIN`, …), and sibling checkouts (upstream `Mindustry`, `Arc`, `main`) sit
  alongside the repo and are referenced relatively (`../Mindustry`, `../Arc`, `../../main`).
- **Keep parity pinned.** Content IDs, `ContentType` ordinals, entity field order, bundle keys
  and sprite region names are append-only ABI. A change touching a `parity/checksum_registry.json`
  contributor bumps `CHECKSUM_VERSION` and re-records every golden in the same change.
- **Parity fix commits are pre-authorized.** Commit each verified fix directly without asking,
  with `Fixes EV-####` in the message; never push.
- **Verify before finishing.** Run the applicable checks above; use `tools/ci.sh` for a
  full gate. New files are UTF-8, LF line endings, no BOM, GPL-3.0-only, and cite the ported
  Mindustry source in the header when they mirror upstream.
- Godot-first and editor-navigable. Prefer **nodes and scenes declared in `.tscn` files** over trees
  built in code; a human should be able to open the project in the Godot editor and navigate/inspect
  the game. Static UI, world scaffolding, autoloads and debug views belong in scenes. When code must
  instantiate nodes (spawner-produced units/buildings/bullets, pooled FX, data-driven list entries),
  add a comment at the instantiation site:
```gdscript
var unit = UNIT_SCENE.instantiate()  # code-instantiated: spawned by WaveSpawner at runtime;
```
  The comment must give the **specific** reason (“spawned at runtime”, “pooled/high-churn”, “count
  driven by server rows”) — “easier in code” is not a justification. Rust owns behavior, not scene
  construction, for static content. Full rule: `HIGH_LEVEL_PLAN.md` §6.6.
